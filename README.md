# ai-teacher

把一篇文章 —— 或者干脆一句话主题 —— 自动变成一条带配音和代码演示的教学视频。自用工具，CLI 优先。

> 要接着往下开发，先看 [HANDOFF.md](HANDOFF.md) —— 那份写的是「现在到哪了、
> 接下来干什么、动手前必须知道的几条」。这份 README 讲的是设计与坑。

## 一句话流程

```
corpus/source.md      你的输入：一篇文章，或一句话主题
      │
      ├─ pnpm plan         AI 写讲稿 + 分镜（带校验，不合格自动重试）
      │                    —— 模型写的那份里没有段号，段号由此推导出来
      ▼
corpus/episode.json   剧本：讲稿分段 + 画面配置
      │
      ├─ pnpm say          配音 + 词级时间戳
      ├─ pnpm storyboard   段号 → 真实时间（顺带切出字幕）
      └─ pnpm video        逐帧渲染 → 合成 mp4
      ▼
out/render/final.mp4
```

## 命令

| 命令 | 作用 | 耗时 |
|---|---|---|
| `pnpm plan [文章\|主题]` | AI 写剧本。参数是**已存在的文件**就当文章，否则当一句话主题（例如 `pnpm plan "Vue3 响应式原理"`）；不带参数读 `corpus/source.md` | 1–4 分钟（含重试） |
| `pnpm plan --dry …` | 只判别「这次按文章还是按主题跑」，不调模型、不写文件 | 瞬间 |
| `pnpm say` | 生成配音 + 词级时间戳 | 30–60 秒 |
| `pnpm storyboard` | 把段号解析成真实时间 **+ 生成字幕**（含外挂 `.srt` / `.vtt`） | 瞬间 |
| `pnpm dev` | 浏览器预览（**有声音**、可拖时间条、字幕可开关） | — |
| `pnpm video` | 一键出片（字幕烧进画面） | 3 分钟视频约 3.5 分钟 |
| `pnpm shot 20000` | 只截第 20000 毫秒那一帧（调试画面） | 几秒 |
| `pnpm shot:cue 3` | 截第 3 条字幕中间那一帧（**校对字幕最顺手**） | 几秒 |
| `pnpm check` | 创作格式与推导的自检（范例、反例、不变量）—— 纯函数，不调模型 | 几毫秒 |
| `pnpm typecheck` | 类型检查，应当是 0 错误 | 几秒 |

## 六条设计约束

**1. 画面 = 时间的纯函数。**
场景组件里**禁止** `setTimeout` / `setInterval` / CSS `transition` / `animation`。
所有视觉状态都由 `t`（毫秒）算出来。这样任意时刻都能「点名渲染」——
逐帧截图才有可复现性。

**2. 播放器可以用真实时间，场景不行。**
预览时以 `audio.currentTime` 为时钟（音画天然同步）；
出片时程序直接调 `window.__seek(t)`。边界就在这一层，别越界。

**3. audio-first：时长是从配音里量出来的，不是拍脑袋定的。**
换音色、改语速，帧数自动跟着变。画面迁就声音，不能反过来。

**4. 对齐靠「句子和元素是同一个对象」，不靠数数。**
模型写的那份里**一个段号都没有**；段号由程序推导（详见下一节）。

**5. 每步产物落盘，改了什么只重跑那一步。**
改讲稿要重跑 `say`；只改画面不用重新配音。

**6. AI 的产出必须过校验才能进管线。**
不过校验就不覆盖 `episode.json`，并把问题清单喂回去让它自己改。

## 画面怎么和声音对齐（核心）

分两层：**模型写的是「创作格式」，渲染器读的是「渲染格式」**，
中间由 [src/plan/authoring.ts](src/plan/authoring.ts) 推导。

### 模型写的那份：句子和它描述的东西是同一个对象

```json
{
  "scenes": [
    {
      "template": "CodeTyping",
      "say": ["先说压缩，图片是页面体积的大头。"],
      "props": {
        "fileName": "compress.js",
        "lines": [
          { "code": "import { resize } from './resize'" },
          { "code": "const w = img.width, h = img.height", "say": "取出原图的宽和高。" }
        ]
      }
    }
  ]
}
```

**每一句 `say` 就是讲稿。** 顺序就是「从上往下读 JSON」的顺序：
先读场景的 `say`，再读它里面每个元素的 `say`。

**任何编号都不归模型**：没有 `parts`、没有段号，也不写「第 N 行」——
段号按 `say` 的顺序推导，代码行的「第 N 行，」由 [addLineNumbers](src/plan/authoring.ts)
按「写了 `say` 的第 N 行」补上（所以上面那句写成「取出原图的宽和高」就够了）。
模型一个数字都不用写。

### 渲染器读的那份：还是段号

推导出来是老样子：讲稿切成 `parts`，每个元素带上 `part`，
`"part": 3` 就是「念到第 3 段的时候，这个元素出现」。

### 为什么要分两层

因为凡是让模型自己数数，它就会数错，而且**每次换一张脸**：

| | 形态 | 校验看得见吗 |
| --- | --- | --- |
| 文章模式 | 某个场景的 `part` 集体早一段，整段画面比声音早一整句 | ✗ 段号全合法，在成片里躺了很久 |
| 主题模式首跑 | `import` 在讲稿里没有对应的句子，模型**偷了一个属于下一行的段号** | ✗ 数字全都合法 |
| 加完铺垫行之后 | setup 行偷了**下一行的讲解**，顺手把后面的编号也对齐了 | ✗ **数字自洽，句子在讲别的事** |
| 换成创作格式之后 | 行号还在模型手里：有 setup 行的三个代码块，都把「第一行」挂在 setup 行上 | ✗ 序数检查照样放行（号是它的） |

根源是同一个：**模型要同时维护两份清单**（讲稿、画面），中间靠**数数**对上。
每加一条规则只能拦住已经出现过的那张脸，拦不住下一种。

所以四次都朝同一个方向收权：**编号一律归程序**。
段号由 `deriveEpisode` 推导，「第 N 行」由 `addLineNumbers` 补 ——
两个都到不了模型手里，模型写一个数就会被 `validateAuthored` 挡下来。
数的人只剩一个，而且它数的是自己刚摆好的顺序，**说出来的编号永远是真话**。

前面三次收权收掉的是**结构**（错一格），第四次收掉的是行号。
剩下的那一半 —— 「这句话说的是不是这一行」—— 是**语义**，四次都没治住，
机器也判不了，见下面「仍有一类例外」。

> 分层还有个好处：`render/`、`build-storyboard`、字幕、编码整条下游**一行都没改** ——
> 它们读的还是老格式。

### 元素可以不写 `say`

不写 `say` = 「讲稿里不专门讲它」，它跟着**场景开头**一起出现。只有三种：

- **代码里的铺垫行**：`import`、setup 这种只为交代上下文、讲稿里**不该**专门讲它的行
  （没人想看「下面我们 import 两个 API」）。
  一个代码块**最多 2 行，而且只能放在最前面**（`LIMITS.maxPreambleLines`，
  越界会被 `checkCodeNarration` 拦下）。
- **幻灯片里跟场景开头一起出现的要点**：几条要点共用开场那一句时，它们都不写 `say`，
  一起跟着那一句出现。（**场景开头也没写 `say` 的话，要点就必须自己写** ——
  否则它没有可以跟的那句话。）
- **终端里的输出行**：它紧跟在自己那条命令后面出现。

**铺垫行为什么要专门开这个口子**：不开的话模型不会报错 —— 它会**偷一个本来属于别的行的段号**
把「每一行都有一句」圆过去，于是从那行往后每个元素都晚一格。
**这不是模型不听话，是那条规则本身做不到。给它开一个明确的出口，比让模型自己找歪路强。**

**「第 N 行」数的是「写了 `say` 的第 N 行」**（铺垫行不数进去）。

这条约定现在**由程序执行**：`addLineNumbers` 按这个口径补号，模型写「第一行」
会被 `validateAuthored` 挡下来（第四次翻车就是它导致的）。于是「编号」这一半
永远自洽了 —— 但要说清楚**它只赢了一半**：`checkCodeNarration` 那条自洽检查
只防「编号对不上」，防不了「编号自洽、句子在讲下一行」（第三、四次翻车都是这样）。
后半句是语义，补不上。
（`episode.ts` 和 `authoring.ts` 的头注释记着这两次打脸的经过。）

两处和行号有关的细节：

- **前缀只加在 `say` 的第一句上**，所以「这一行做完之后会怎样」这类收尾要写成
  数组的第二句 —— 否则程序会把它当成「就是讲这一行的」。
- **行号不算进字数上限**：`plan.ts` 是**先校验、后补号**（见 `addLineNumbers` 的注释）。
  所以落盘字数 = 模型写的 + 4 ×（有讲解的代码行数）。当前这份 13 句，
  就是多 52 字（约 10 秒）—— 量过，不是估的。

## 有哪几种画面

三种。都是「给一个 `t`，算出这一帧长什么样」，没有别的。

| template | 画什么 | 什么时候用 |
| --- | --- | --- |
| `SlideBullets` | 标题 + 要点逐条淡入 | 交代脉络、列结论 |
| `CodeTyping` | 代码窗口，逐字打出来 | 讲**代码长什么样** |
| `Terminal` | 终端窗口，命令逐字打、输出整行出现 | 讲**把它跑起来会发生什么** |

`CodeTyping` 和 `Terminal` 长得像但分工不同：一个讲代码本身，一个讲运行结果
（构建输出、起服务、测试失败）。让 Terminal 去念一段代码是误用 ——
观众要的是「敲下去之后屏幕上多了什么」。

```json
{
  "template": "Terminal",
  "say": ["把它跑起来看看。"],
  "props": {
    "title": "运行构建",
    "prompt": "$",
    "lines": [
      { "text": "pnpm build", "kind": "command", "say": "先构建。" },
      { "text": "✓ built in 363ms", "kind": "output" },
      { "text": "pnpm dev", "kind": "command", "say": "再起开发服务器。" },
      { "text": "➜  Local: http://localhost:5173/", "kind": "output" }
    ]
  }
}
```

两条规则和 CodeTyping 是同一套心智模型：**`command` 必须写 `say`**
（讲一条、出现一条），**`output` 不写 `say`** —— 它是程序吐出来的，
紧跟在自己那条命令打完之后出现。输出逐字打会很怪，真实终端也不这样。

光标只在**有命令正在打字**时出现，打完就消失。不是常驻闪烁 ——
常驻闪会每 530ms 把复用判据打回「在变」，白白吃掉一帧的复用率。

### 加一个新模板要动 5 处

模板名是裸字符串，没有注册表（只有 3 个模板，做注册表是过度设计）。
加一个模板，这 5 处**必须同时改**：

1. `src/render/scenes/Xxx.vue` —— 组件本身
2. `src/render/scenes/sceneState.ts` —— 加 `xxxStateAt(t, props)`：把「这一帧
   所有随时间变化的值」算出来。**组件和复用判据都调它**，不许各算一遍
3. `src/render/stage/Stage.vue` 的 `TEMPLATES` —— 注册组件
4. `src/render/stage/Stage.vue` 的 `SIGNATURES` —— 登记帧签名。
   **漏了这处不会报错，画面会卡住不动**（判据认为它永远在变 / 永远不变）
5. `src/plan/episode.ts` 的 `TEMPLATE_NAMES` —— 白名单。漏了模型就能写出
   不存在的模板名，`Stage.vue` 找不到组件时会**安静地画一片空白**

外加 `build-storyboard.ts` 加一支（段号 → `atMs`），以及 `prompt.ts`
和 `corpus/example-episode.json` 里的说明和范例 —— 模型主要靠范例学形状，
只在提示词里写 prose 它多半不会用。

> 已经有一条兜底：`validateEpisode` 会拿 `TEMPLATE_NAMES` 拦住拼错的模板名。
> 这是补的第 5 处 —— 在此之前模板名写错会一路穿到渲染，什么都不报。

## 字幕怎么来的（`src/plan/subtitle.ts`）

字幕**不需要 AI 参与**，它是 `pnpm storyboard` 的副产物：

- **断句用讲稿原文** —— 词表里没有标点，拿它拼出来是一坨没有标点的字。
- **时间用词级时间戳** —— 但词级时间戳只给「每个词什么时候开始念」，
  一条字幕的结束时刻往往落在某个词念到一半的地方。所以要**插值出字级时间**：
  一个词读 350ms、有三个字，第 2 个字就落在 +117ms 附近。
- **段（`parts`）是不可跨越的边界** —— 一条字幕绝不跨段并排。
  段本来就是按语气切的，比任何启发式规则都靠谱。
- **断句顺序**：句号优先，逗号其次，都没有才硬切。
  第一版是「凑够 18 个字就切」，切出来是「…很简单， / 结果做出一条完整管线。这」
  —— 观众读到的永远是半句话。
- **一条字幕 = 一行**，字数上限（26 字）直接对齐「一行放得下多少字」。
  折行代码仍然留着（兜底），但正常不会再触发 —— 实测 39 条全部一行。
- **切点只落在词首**，绝不切在词中间。掩码标的是「字与字之间的缝」，
  和「第几个字符」差一格就会切出「六百五十|九KB」这种。
- **折行按词边界**，并按显示宽度挑最平衡的断点。
  只按字数切会切出「一百五十 / 四KB」「dataU / RL」这种。
- **代价**：为了守住「一行」，偶尔会切出偏短的一条（实测 3 条落在
  1.5~2.0 秒，最短 1.475 秒）。这是故意的取舍：切碎只是这一条短一点，
  折行则会让排版乱掉。

字幕是**时间的纯函数**（`Stage.vue` 里的 `Subtitle.vue` 那一层），
所以逐帧渲染天然带上它，不需要 ffmpeg 的 subtitles 滤镜，
也不需要额外跑一遍编码。

### 同一个 `cues`，三种出口

| 出口 | 谁用 | 什么时候写 |
|---|---|---|
| 画面内烧录（`Subtitle.vue`） | 成片本身 | 逐帧渲染时天然带上 |
| `out/render/subtitles.srt` | B 站、大部分播放器 | `pnpm storyboard` 顺带写 |
| `out/render/subtitles.vtt` | YouTube、网页播放器 | 同上 |

外挂那两个**不单独开命令**：数据就是 `cues`，重跑 `storyboard` 就一起刷新，
不可能出现「改了字幕忘了导」。格式化在 `src/plan/subtitle-export.ts`，
两种格式只差三处（序号、毫秒分隔符用逗号还是点、有没有 `WEBVTT` 头）。

写文件走 Node 的 `writeFile`，UTF-8 **不带 BOM** —— 别改成用 PowerShell 的
`-Encoding utf8` 中转，那会写进 BOM，字幕开头多一个乱码方块。

用 `cue.text` 而不是 `cue.lines`：`lines` 是给 1080p 画布折好的行，
播放器自己会按窗口宽度折，硬塞进去反而更难看。

想改字幕，重跑 `pnpm storyboard` 就够了 —— 不用重新配音，也不用重新生成剧本。

## 踩过的坑（这些比代码值钱）

**渲染**

- **不能用 `file://` 打开构建产物。** 浏览器会以跨域为由拦掉 `<script type="module">`，
  页面根本不启动。必须在脚本里起一个本地静态服务器。
- **Playwright 自带的 ffmpeg 是精简版**，没有 mp4 封装器、没有 libx264，
  传 `-movflags` 直接报 `Unrecognized option`。装 `@ffmpeg-installer/ffmpeg`。
- **TTS 返回的词表里没有标点和空格。** 拿讲稿原文去比对永远对不上，
  两边都得先「只保留汉字/字母/数字」再比。
- **PowerShell 的 `Set-Location` 不改变 .NET 的工作目录。**
  用 `[System.IO.File]::WriteAllText()` 传相对路径会写到别的目录去。
  一定用绝对路径。
- **PowerShell 5.1 的 `-Encoding utf8` 会写 BOM。** ffmpeg 的 concat 列表、
  `.gitignore` 都会被 BOM 弄坏。
- **`Get-Content` 读无 BOM 的 UTF-8 会按 GBK 解**，中文注释会被写坏。
  用 `[System.Text.Encoding]::UTF8` 显式读。

**音画对齐**

- **画面元素必须绑到某一句讲解上。** 没绑的元素会按固定间隔自己冒出来，
  而讲解早就讲到别处了。改契约之后这一条由结构保证：**不写 `say` 的只有那三种**
  （铺垫行、跟场景开头出现的要点、终端输出行），其余一律各有一句。
- **场景不能挂太久。** 如果某几段讲解没有对应画面，上一个场景会一直挂在屏幕上 ——
  观众听到新话题、看到旧画面。这是「音画不同步」最常见的原因。
  （现在这条会由 `checkEditorial` 报出来：一个场景最多 6 句讲稿。）
- **场景引用的段号不能越过下一个场景的开始**，否则那个元素永远不会出现。
  （改契约之后模型写不出这种段号了 —— 它压根不写段号；这条现在只防手改的 `episode.json`。）
- **「第一行/第二行」这类序号很脆弱 —— 所以现在由程序说。**
  这里原来写着「改成直接描述这行在做什么更稳」，但**范例自己就在用序号**，
  模型当然跟着用 —— 于是那条建议从没生效过。
  后来把数法定死（「第 N 行」= 写了 `say` 的第 N 行），并加了 `checkCodeNarration`；
  **它确实能在带着那个 bug 的产物上抓出来**，但只赢了一半：第三、四次翻车时
  模型把编号顺手对齐了，数字全对、句子在讲下一行，这条检查一声不吭。
  现在**模型不写行号**了（`addLineNumbers` 补），编号那一半不再可能错；
  「句子在讲下一行」那一半是语义，补不上。
- **整体错一段，校验查不出来。** 校验只管「段号递增、不越界、不跨场景」——
  把某个场景的 part 全部统一 -1，照样条条合法。可画面会比声音早一整句。
  这不是理论：`episode.json` 的 s6（8 行代码）和 s7 就是这样，**在成片里
  潜伏了很久**，直到 s7 换成 Terminal 逐行对讲解才露出来。
  **现在这一类在结构上不可能了**（模型不写段号），但这条教训仍然值钱：
  它能潜伏那么久，是因为校验的输出看起来「条条合法」。
  剩下的语义错位仍然只能读 `pnpm storyboard` 打印的那份对照 ——
  每个元素下面写着它的讲解，**逐行读一遍**，不要只看时间。**别当成已经解决了。**

**字幕**

- **字坐标和原文下标是两套东西，混用必翻车。** 字坐标里没有标点（一个标点占 0 格），
  原文下标里标点占一格。「给博客加图片，本以为很简单，…」里第 22 个字
  在原文里是第 25 个字符。所有「边界对不对」的 bug 都是这两套坐标混了。
- **段边界绝不能用「时刻反推词边界」来算。** Edge 会把「管线。」和「这条管线…」
  并成同一个词条，用时刻一推就晚一个词 —— 于是每条字幕都多咬掉下一段的第一个字。
  要用**段的文字**去讲稿里顺序查找，得到确定的字符边界。
- **覆盖率检查抓不到「串位」。** 每个字都在，只是被划到了隔壁字幕 ——
  字数校验全过，画面却是半句话。所以还要单独校验「每个切点都在词首」。
- **标点必须显式归给左边那条字幕。** 边界正好落在标点之后时，
  这个标点谁都不认领（前一条切到标点前，后一条从标点后开始），
  画面上就是「结果做出一条完整管线」少个句号。
- **折行不能只按字符数。** 汉字和英文宽度不同（`canvas` 比同长度的汉字窄得多），
  而且按字符数切会把数词、英文单词劈开。要按显示宽度挑断点，且只在词边界断。
- **`pnpm shot:cue 3` 是校对字幕最快的路子** —— 直接截出第 3 条字幕的正中间那一帧。

**AI 生成**

- **提示词里写了却没校验的约束，等于没写。** 例如「全片不超过 900 字」——
  不加校验器，模型超了也没人管。
  这一条对**下限**同样成立，而且吃过两次亏：最早写的是「大约 300 到 900 字」，
  那个 300 一直没校验，于是模型两次都贴着它写 ——
  325 字（55 秒）、改完目标之后 718 字（约 2 分钟），**两次都没进 800–900 的区间**。
  现在 `LIMITS.minTotalChars` 抬到 **700**，让它变成**会触发重试**的硬约束。
  教训比这条规则本身大：**只写在提示词里的目标，模型会挑自己看得见的那条线来贴。**
- **校验报错要翻译成「具体怎么改」。** 只说「找不到 cue」模型不知道该加还是该删；
  说清楚「要么补一段讲解，要么把这个字段删掉」它才改得对。
  （顺带查出来：`repairHint` 里 `必须严格递增` / `行代码，超过` 两个匹配键，
  从来没匹配上过任何一条报错文案 —— 等于没写。改格式时一并修了。
  这类「写了但没生效」的代码，和上面那条约束是同一个毛病。）
- **每一次翻车都应该变成一条机器能自动检查的规则。**
  —— 这条原则本身后来被证伪了四次，现在得补半句：
  **先问「这类错误为什么可能发生」，再决定是加规则还是改契约。**

  拿「画面漂一格」当例子，它撞了四次，每次换一张脸：

  | 次 | 形态 | 怎么收场 |
  | --- | --- | --- |
  | 1 | 某个场景的 `part` 集体早一段 | 人眼逐行读才发现；改产物 |
  | 2 | `import` 偷了一个属于下一行的段号 | 开「铺垫行」出口 + 序数检查 —— **这次治住了** |
  | 3 | setup 行偷了**下一行的讲解**，编号还顺手对齐了 | 数字自洽，那条检查看不见 |
  | 4 | 换成创作格式**之后**：有 setup 行的三个代码块，把「第一行」挂在 setup 行上 | 序数检查照样放行 —— **号是它自己写的** |

  第三次是转折点：模型**完全满足**了我们定的约定，句子却在讲下一行 ——
  也就是说，能拦住的是「已经出现过的那张脸」，拦不住下一种。
  于是不再加规则，改成让模型**根本不写段号**（创作格式，段号由程序推导）。

  第四次说明**收权收得还不够**：段号收走了，行号还在模型手里，
  而它错了之后**编号会自洽**（模型顺手重编号）—— 那条序数检查因此永远抓不到。
  所以行号也收了（`addLineNumbers`）。这一类错误现在不是「被拦住了」，
  是**没有可数错的东西**。

  **但仍有一类例外，是刻意接受的**：**语义**层面的不匹配。
  校验只管结构 —— 段号、长度、画面装不装得下 —— 管不了「讲稿说的是不是真的」。
  主题模式真跑撞出来的那一种：
  - **凭空编 API**：实测**没发生**（`reactive` / `effect` / `toRefs` 逐个核过），
    但主题模式没有原文兜底，按设计它迟早会发生。这一类**查不了**，只能人眼。
  - **句子在讲下一行**：第四次真跑（`Vue3 响应式原理`）里，
    `const state = reactive({ n: 0 })` 上挂着「第一行，effect 注册一个副作用函数」，
    而 `effect(...)` 在下一行。**行号收走之后它仍然是错的** ——
    编号不用数了，但「这句话说的是不是这一行」还是语义。
    （同一份产物里还有一条：讲代码第四行的那句跑到了下一张幻灯片上。
    这一条**现在会被拦下** —— 场景的 `say` 里不许出现「第 N 行」。）

  兜底只有一招：`pnpm plan` 跑完会把讲稿和「代码行 ↔ 它的讲解」全打出来，
  `pnpm storyboard` 再打一遍带真实时间的 —— **逐行读，别只看时间**。
  别拿「先出大纲人工确认」那种重流程去「修」它，
  那会毁掉「一句话直接出片」这件事本身。

## 渲染怎么提速的（静止帧复用）

先量，再动手：

| | 每帧耗时 |
|---|---|
| `page.screenshot()` | 78.9 ms |
| `page.evaluate(__seek)` | 13.4 ms |
| 内容与上一帧**完全相同**的帧 | **79%** |

截图占八成半，而八成的帧是在重复截同一张画面。所以提速的办法不是「截图更快」，
而是**根本不截图**：`frames.ts` 每帧先问一句 `window.__static(cur, prev)`
（这一帧的时刻、**上一帧的真实时刻**），回答「这张画面和上一帧一样」
就把上一帧的 PNG 复制过来。

实测（**全片** 4869 帧、162.3 秒）：

```
关复用 481 秒  →  开复用 138 秒   （3.5 倍）
复用 3882 帧（80%），复用一帧 6.1ms，渲染一帧 115.7ms
其中每帧问一次 __static 3.0ms，复制一帧 3.1ms
```

（更早的两个数字留作对照：前 60 秒 1800 帧 233s → 73s（78%）；
只复用幻灯片时全片 8.49 分钟 → 3.17 分钟（59%）。）

判据在 `Stage.vue` 里（画面是时间的纯函数，所以判据也是），分两块：

1. **场景内部**：比较前后两帧的「帧签名」。签名是「给一个时刻，交出这一帧
   画面上**所有随时间变化的值**」，比如代码场景是
   `{ 第几行激活, 光标显隐, 每行打出几个字 }`。签名相同 ⇒ DOM 相同 ⇒ 像素相同。
   签名函数住在 `scenes/sceneState.ts`，**组件渲染和复用判据调的是同一份**。
2. **字幕层**（独立的一层、跨场景连续）：两帧得落在同一条字幕里，
   且那条字幕已经淡入完。

**为什么按元素而不是按场景**：一张幻灯片的动效可能持续 16 秒
（要点在不同时刻出现），但那 16 秒里 89% 的帧画面根本没变 ——
它们都在「上一条要点稳定了、下一条还没出现」的空档里。
按整个场景一刀切时复用率只有 17%。

**怎么确认它没把画面弄坏**：`FRAMES_NO_REUSE=1` 关掉复用跑一遍，
和开着跑一遍，逐帧比对 PNG 的 MD5 —— 必须完全一致。
实测全片 4869 帧全同。

**踩过的坑（都是实测踩出来的，不是想出来的）**

- **不要用硬链接。** 想的是「硬链接不复制数据，几乎不花时间」，
  实测恰好相反：在这种有几万个文件的目录里 `link()` 要 47ms/次，
  而 `copyFile()` 只要 1.5~6.5ms —— 复制快 7 倍以上。
  （另外 NTFS 单文件硬链接上限 1024，超了直接报错。）
- **判据不能写在「页面当前时刻」上再做决定。** `__static` 是时间的纯函数，
  要在 `__seek` **之前**问；先 seek 再问的话复用帧也白付 11ms 的 seek。
  反过来说，问的时候页面还停在上一帧，所以判据里**不能**读任何 DOM 状态。
- **判据绝不能在两个地方各算一遍。** 代码场景一开始干脆不参与复用：
  我给它写过判据（逐字打字区间 + 光标闪烁），但一直有边界漏洞 ——
  全片实测仍有 29 帧被误判成静态，而那些帧一旦被复制成上一帧，画面就卡住了。
  根因是判据在 `Stage.vue` 里拿 `atMs` 去「推」第几个字符打出来了，
  等于把 `CodeTyping.vue` 的 `Math.floor(elapsed / CHAR_MS)` 抄了第二遍 ——
  两个地方各算一遍同一个公式，在边界上必然错开一两个字符。
  现在公式抽到 `scenes/sceneState.ts`，两边调同一个函数，
  这种错位在结构上不可能发生。
- **「上一帧」必须是真实值，不能用帧率反算。** 判据原本写成 `ms - 1000/fps`，
  那是 33.333；而 `frames.ts` 里真实的上一帧是 `Math.round((f-1)*1000/fps)`，
  是 33 或 34。差的那零点几毫秒正好踩在字幕/字符出现的整数边界上。
  现在由 `frames.ts` 把 `prev` 直接传进页面。
- **签名必须列全所有依赖 `t` 的东西。** 以后给场景加了新动效却忘了写进
  `sceneState.ts`，判据就会漏项 → 画面卡住。防呆只能靠逐帧对拍。
- **对拍只能证明「没错」，不能证明「有效」。** 这个功能第一版复用率恒为 0%
  （因为判据问错了对象），而对拍照样全绿。
  所以两个都测：对拍查正确性，`__static` 命中率查有效性。

## 已知限制

- **渲染速度**：全片已实测 —— 4869 帧，关复用 481s → 开复用 138s（3.5 倍），
  复用率 80%，逐帧 MD5 0 差异。再往下可做的：
  多场景并行渲染、换 CDP 截图绕开 Playwright 的封装。
- 画面类型有三种：幻灯片、代码打字、终端演示。
- 字幕只有中文一种语言。画面内烧录和 `.srt` / `.vtt` 都有
  （后两个由 `pnpm storyboard` 顺带写，见「字幕怎么来的」）。
- 讲稿的语义正确性靠模型自觉，程序只能保证结构正确、
  「每个元素都有自己的讲解」和「讲稿的顺序就是画面的顺序」。
  **「这句话说的是不是这一行」仍然是语义，查不了** —— 只能读 `pnpm storyboard` 那份对照。
